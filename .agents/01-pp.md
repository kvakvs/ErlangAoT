# Erlang preprocessor implementation plan

Status: steps 1–2 implemented, 2026-09-18. Boost.Parser integration, owned sources,
incremental lexing, and OTP 29.1 scanner fixtures are available. This expands step 2 of
[`00-plan.md`](../00-plan.md).

## Scope and reference baseline

Implement the preprocessor in C++23, using Boost.Parser for composable parsing
rules. Keep it inside the host compiler, independent of LLVM and the runtime.
The feature checklist comes from the Erlang
[Preprocessor chapter](https://www.erlang.org/doc/system/macros.html).

Target OTP 29. The local reference is now pinned to `OTP-29.1`, commit
`751f87b703fe5948607d08e82599ce644b772e76`, in gitignored `references/otp/`.
Record this baseline alongside compatibility fixtures. Use its documentation,
source, and actual behavior together; the public documentation changes over time.
See [the OTP test inventory](01-pp-otp-tests.md) for suites, concrete cases, and
findings from source inspection. The reference suites have not yet been run.

This work includes lexical support and the small expression/term parsers needed
by preprocessing. Full Erlang AST parsing, record expansion, parse transforms,
semantic analysis, and code generation remain separate work. Other epp services,
such as external documentation-file ingestion, are outside this chapter's scope.
Internal token handling below does not select the public stage interchange
format. Reserve `compiler/src/stage_readers/preprocessed/` only; do not design
or implement intermediate readers here.

## Implementation sequence

### 1. Establish Boost.Parser integration and the test oracle

Implemented: standalone pinned headers, recursive probe, source offsets and
failure tests, optional version-checked epp oracle. `parsable_iter` requires
character code units; the compile-time probe rejects a Token iterator. Use
Boost.Parser for characters and an explicit token cursor in later steps.

- Pin a tested Boost release containing Boost.Parser. Add compiler-local CMake
  dependency wiring with an installed/local-source route; runtime-only builds
  must not discover or download Boost. Retain C++23 and optional C++26 builds.
- First compile a small grammar for an identifier, a directive envelope, and a
  nested argument sequence. Exercise success, failure, source offsets, recursive
  rules, and rollback. Avoid global state changes inside backtracking actions:
  parse a directive value first, then apply it once.
- Investigate the selected version's custom-parser extension with a token cursor.
  Do not assume that arbitrary `Token` ranges work with character-oriented
  primitives. Prove this adapter before building token grammars on it. If the
  extension cannot support it cleanly, use Boost.Parser for lexical rules and
  character subgrammars, with a small explicit token cursor for orchestration.
  Do not stringify/re-lex expanded tokens merely to fit the library API.
- Keep Boost types behind implementation boundaries. The project owns tokens,
  source records, directive values, and diagnostics. See the
  [Boost.Parser documentation](https://www.boost.org/doc/libs/latest/doc/html/parser.html)
  and its [custom-parser tutorial](https://www.boost.org/doc/libs/latest/doc/html/boost_parser/tutorial.html).
- Build an optional OTP oracle harness using `epp:scan_erl_form/1` for expanded
  tokens and diagnostic events. Use `epp:parse_erl_form/1` only where comparing
  valid complete forms is useful. Record token kinds/values and selected source
  annotations; keep fixture serialization private to tests. The APIs are
  documented in [epp](https://www.erlang.org/doc/apps/stdlib/epp.html).

Acceptance: the integration probe builds, the harness records one successful and
one erroneous fixture, and absence of OTP explicitly skips oracle tests while
ordinary tests remain runnable.

### 2. Implement source ownership, locations, and lexical rules

Implemented: shared source/spelling lifetimes, encoding and location mapping,
structured lexical diagnostics, incremental tokens/forms, OTP 29 literals/sigils
and based numbers. Five checked-in scanner fixtures match live OTP 29.1 exactly.
C++23/C++26, ASan/UBSan, Lizard, and clang-tidy pass on macOS arm64.

- Add owned source buffers, file identities, physical offsets, line/column
  tracking, and logical source locations. Tokens retain spelling and decoded
  values where needed. Keep expansion and include provenance separately from
  original spelling locations.
- Decode each file independently. Cover UTF-8, Latin-1 encoding declarations,
  invalid input, LF/CRLF, and missing final newlines. Follow
  [epp's encoding rules](https://www.erlang.org/doc/apps/stdlib/epp.html).
- Use reusable Boost.Parser rules for Erlang lexical categories. Cover atoms,
  variables, quoted atoms, numbers, characters, strings, comments, punctuation,
  and longest-match operators. Include the pinned OTP 29 string forms and sigils;
  do not let macro punctuation inside a literal become preprocessing syntax.
- Recognize Erlang form-ending dots separately from decimal points, record field
  access, and dots inside literals. Preserve token spelling needed later by
  stringification. Check results against
  [erl_scan](https://www.erlang.org/doc/apps/stdlib/erl_scan.html).
- Scan incrementally by forms so feature directives can affect subsequent
  keyword classification. Avoid eagerly tokenizing the entire module with one
  fixed keyword set.

Acceptance: lexical fixtures match the pinned scanner, including multiline
literals containing apparent directives and delimiters.

### 3. Build the form driver and directive parser

- Create one preprocessing session per input module. It owns the macro table,
  include stack, conditional stack, feature state, and contextual macro state.
- Collect forms using lexical boundaries, not lines. Classify preprocessing
  directives at form starts and pass ordinary forms through for later parsing.
- Parse directive envelopes into explicit values. Capture macro bodies as token
  sequences; they need not be complete Erlang expressions. Recognize supported
  directives precisely and report malformed operands or missing terminators.
- Do not treat arbitrary attributes as preprocessing commands. Detect misplaced
  directives inside function forms without implementing the complete parser.
- Introduce stable diagnostic categories and recover at a safe form boundary
  when possible. Every recovery path must consume input or terminate.

Acceptance: multiline directives work, unknown ordinary attributes survive, and
malformed preprocessing syntax has useful locations without hanging.

### 4. Store definitions and implement object macros

- Represent a macro key as a name plus either object form or parameter arity;
  object form and arity zero must remain distinct. Retain definition locations.
- Parse and validate names, formal parameters, duplicate parameters, and bodies.
  Establish predefinitions before reading source. Keep predefined macro entries
  distinguishable from user definitions.
- Implement sequential definition visibility, object expansion, redefinition
  diagnostics, and `-undef`. Verify removal across overloads, removal of missing
  names, and interactions with predefined names against OTP.
- Expand nested references at use time. Test a referenced macro defined after
  the referring definition but before invocation; do not eagerly expand stored
  bodies. Capture undefined references and direct/indirect cycles with traces.
- Include initial-definition fixtures for a name alone and a name with an Erlang
  term value, using the [epp predefinition API](https://www.erlang.org/doc/apps/stdlib/epp.html)
  as the reference. CLI spelling is added in step 13.

Acceptance: source order, undefinition, redefinition, nested object expansion,
and per-module isolation match the oracle.

### 5. Implement parameter substitution and overload resolution

- Collect actual arguments without parsing them as full expressions. Track
  parentheses, lists, tuples/maps, binaries, and keyword-delimited expressions.
  Handle commas within `case`, `receive`, `try`, `begin`, `if`, `maybe`, and fun
  bodies; distinguish fun references and fun types from fun expressions needing
  `end`. Seed these cases from OTP's `fun_type_arg` regression.
- Substitute parameter tokens structurally. Avoid replacement inside strings,
  quoted atoms, or longer identifiers. Preserve caller spelling and provenance.
- Implement dispatch among object definitions and arities. Test zero-argument
  calls, mixed overloads, missing argument lists, and wrong arities. In
  particular, test an object macro naming a function followed by `()` and the
  precedence rules when parameterized overloads also exist.
- Rescan replacements according to OTP semantics. Compare nested invocations,
  reused and unused arguments, macros in arguments, and partial syntax bodies.
  Distinguish repeated finite use from recursive expansion; a global visited-name
  set is insufficient.
- Bound expansion depth and produced token count with explicit resource-limit
  diagnostics. Keep these implementation limits distinct from language errors.

Acceptance: macro-heavy fixtures pass, including nested block expressions and
expansion that becomes valid syntax only after substitution.

### 6. Implement argument stringification

- Recognize `??` references in replacement bodies and connect them to formals.
- Keep original argument tokens available independently of expanded arguments.
  Use oracle cases to establish expansion timing, token spacing, escaping, and
  literal spelling. Test nested macro references, quoted atoms, strings, Unicode,
  operators, and arguments with comments or line breaks.
- Produce an Erlang string token with correct value and source provenance.
  Diagnose invalid stringification operands in the same circumstances as OTP.

Acceptance: compare exact string values, not just parse success or a pretty
printer's output. Establish the behavior from the
[stringification section](https://www.erlang.org/doc/system/macros.html#stringifying-macro-arguments).

### 7. Implement conditional structure and skipped forms

- Track parent activity, whether a branch has already been selected, directive
  family, whether `else` occurred, and opening location for every nesting level.
- Implement definedness tests and branch transitions. Leave a condition-evaluator
  hook for step 10; until then, diagnose active unsupported expression conditions.
- In inactive branches, suppress definitions, includes, ordinary expansion, and
  user diagnostic directives while still recognizing conditional structure.
  Determine scanner-error behavior in skipped text from OTP; do not promise
  arbitrary malformed bytes can be skipped.
- Cover unmatched terminators, duplicate `else`, illegal branch ordering, and
  unterminated groups. Verify which conditional families accept `elif` and how
  structural state behaves at include boundaries.

Acceptance: nested include guards and inactive undefined references behave
correctly; skipped includes perform no filesystem lookup.

### 8. Implement include resolution and nesting

- Separate file access from resolution policy, with injectable filesystem,
  working directory, include paths, environment, and application-directory map.
- Implement absolute paths, the chapter's relative search order, and substitution
  of the leading environment-variable component, including an unset variable.
  Verify nested-header lookup and repeated include-option ordering using fixtures
  with conflicting candidate files. Refer to
  [File Inclusion](https://www.erlang.org/doc/system/macros.html#file-inclusion).
- Implement application-relative `include_lib` lookup through a configured ordered
  application search path. Match the selected OTP application's directory in
  oracle tests. A native tool has no Erlang code server: document this resolver
  input explicitly instead of guessing a version by lexicographic directory sort.
  Check OTP's ordinary-path fallback behavior before finalizing lookup order.
- Push and restore source context, scan included files with their own encoding,
  and preserve macro changes after returning. Verify feature and conditional
  state separately rather than restoring the whole session indiscriminately.
- Retain both physical file identity and user-visible path spelling. Support host
  Windows drive/UNC paths and POSIX paths; lookup happens on the compiler host,
  independently of the executable's target architecture.
- Permit repeated inclusion and terminating guarded recursion. Do not reject
  every repeated active path: include guards can make it valid. Bound include
  depth and diagnose runaway inclusion with the include chain.

Acceptance: deterministic path-collision fixtures, missing applications/files,
guarded cycles, and restoration after includes pass on supported host platforms.

### 9. Implement contextual and compatibility macros

- Track module declarations after expansion, including quoted module names.
  Generate module/file/line values on demand rather than freezing them when a
  macro is defined. Test nested includes, indirect macros, and use before a
  module declaration. Support logical `-file` mapping insofar as it affects these
  macros and diagnostics, retaining physical origins independently.
- Implement a limited function-header recognizer over expanded forms for function
  name/arity. Cover multiple clauses, guards, nested funs, and macro-generated
  names/arguments. Prevent circular dependence between header expansion and
  function-context lookup; diagnose unsupported contexts according to OTP rather
  than guessing from the nearest textual function name.
- Proposed compatibility policy: `OTP_RELEASE` reports the selected major
  language baseline, initially 29; `MACHINE` yields the documented `'BEAM'` value
  for source compatibility. Document that these are compatibility values in this
  native compiler, not claims about its host runtime or output format. Do not
  derive either from CPU architecture or an incidental installed OTP.
- Verify reserved-name definition/overload/undefinition behavior per builtin.
  Feature-query macros are completed with their state model in step 11.

Acceptance: every non-feature predefined macro has direct, indirect, included,
and invalid-context coverage, following the
[predefined macro list](https://www.erlang.org/doc/system/macros.html#predefined-macros).

### 10. Parse and evaluate preprocessing conditions

- Build a Boost.Parser expression grammar for the condition subset, with explicit
  precedence and associativity. Eliminate left recursion in combinator rules.
  Keep its expression representation local until the full parser needs reuse.
- Expand macros, validate the expression, then evaluate through a closed set of
  supported operators and guard BIFs plus the definedness pseudo-function. No
  arbitrary calls, host-language evaluation, or runtime execution is involved.
- Enumerate the pinned OTP guard syntax and permitted BIFs before implementation.
  Test qualified/unqualified calls and record-related cases; coordinate any
  context-sensitive cases with the later parser. Use
  [Guard Expressions](https://www.erlang.org/doc/system/expressions.html#guard-expressions)
  and the pinned epp implementation to resolve the precise subset.
- Implement Erlang term/value behavior needed by those operations, including
  arbitrary-precision integers, floats, comparisons, exact equality, boolean
  operators, and short-circuiting. Select a compiler-local integer facility;
  do not depend on the future runtime's term representation or C++ truthiness.
- Establish OTP outcomes for non-boolean results, invalid guard expressions,
  evaluation failures, unbound variables, and conditions in already-skipped
  branches. Separate syntax validation from evaluation so short-circuiting cannot
  accidentally admit forbidden syntax.
- Connect evaluation to the conditional state machine and finish `if`/`elif`.
  A staged subset is acceptable during development, but every unsupported valid
  case must be explicit; full chapter coverage requires completing the subset.

Acceptance: a table-driven operator/BIF suite and nested conditional fixtures
match OTP outcomes, including overflow-sized integers and skipped evaluations.

### 11. Implement feature configuration and query macros

- Capture the pinned release's feature catalog, lifecycle states, defaults, and
  keyword changes in versioned compiler data. Do not discover them dynamically
  from an arbitrary host OTP installation.
- Implement per-module configuration from initial options and directives. Track
  the legal module prefix, including includes and preprocessing directives;
  reject late changes with the correct source location.
- Distinguish available from enabled, and enforce the rules for permanent,
  rejected, experimental, approved, and unknown features. Implement both query
  macros with validated operands. See the
  [feature lifecycle and configuration rules](https://www.erlang.org/doc/system/features.html).
- Update subsequent lexical classification when configuration changes. Verify
  interaction with skipped branches and included headers.
- Keep baseline feature metadata distinct from implementation completeness.
  Preprocessing compatibility does not imply the full parser/backend implements
  a feature; those stages must explicitly diagnose unsupported constructs.

Acceptance: directive placement, state transitions, defaults, keyword effects,
and query results match the pinned release.

### 12. Implement diagnostic directives and finish error handling

- Parse diagnostic operands with a reusable local Erlang-term grammar, sharing
  applicable literal rules from step 10. Verify macro expansion, accepted term
  shapes, and rejected expressions against OTP.
- Emit structured warning/error records carrying the supplied term and source
  context. Warnings continue; errors mark the session unsuccessful. Recovery may
  collect further diagnostics but must not return success afterward.
- Test suppression in inactive branches and invocation from includes. Complete
  diagnostics for macro cycles, malformed arguments, path failures, conditional
  imbalance, and exhausted resource limits.

Acceptance: distinguish warning-only success from preprocessing failure and
preserve useful include/expansion traces for both, covering
[the diagnostic directives](https://www.erlang.org/doc/system/macros.html#error-and-warning-directives).

### 13. Integrate the driver and complete compatibility validation

- Add an explicit preprocessing-check CLI mode, include paths, initial macro
  definitions, application lookup configuration, and feature options. Choose
  spellings consistent with the existing CLI; document duplicate/conflicting
  options and multiple-input behavior. Parse initial values as Erlang terms.
- Keep preprocessing-check success distinct from successful compilation while
  later stages remain unimplemented. Do not write executable output in this
  mode. Public preprocessed output and its format remain a separate decision.
- Consolidate oracle comparisons over every coverage row and feature interaction.
  Preserve token values and order; normalize only fixture-specific paths and
  deliberately irrelevant annotations. Test important locations separately.
  Treat OTP's implicit file attributes explicitly in the comparison adapter.
- Use generated bounded macro/conditional inputs to test progress, source
  ownership, expansion limits, and reproducibility. Add representative real
  Erlang headers as smoke fixtures with recorded provenance and baseline.
- Validate macOS arm64, Linux x86/ARM, and Windows x86-family host builds; report
  unavailable platform checks as outstanding. Run focused CTest suites and
  sanitizer checks where supported, plus existing CLI regression tests.
- Update README, architecture/file notes, and this checklist with implemented
  scope and remaining gaps. Completion requires evidence for all chapter features,
  not merely recognition of their directive names.

Acceptance: preprocessing-check mode works without an installed OTP, reference
tests run when the pinned OTP is supplied, and the runtime remains independent.

## Planned implementation locations

These are proposed files; create them as their steps start. Keep related small
helpers together and split only when responsibilities warrant it.

| Location                                           | Responsibility                                                   |
| -------------------------------------------------- | ---------------------------------------------------------------- |
| `cmake/CompilerDependencies.cmake`                 | Compiler-only Boost discovery/version policy                     |
| `compiler/src/source/source_manager.{hpp,cpp}`     | Buffers, encodings, physical/logical locations                   |
| `compiler/src/diagnostics/diagnostic.{hpp,cpp}`    | Diagnostic records and source rendering                          |
| `compiler/src/lexer/token.hpp`, `lexer.{hpp,cpp}`  | Token ownership/spelling, composable lexical rules               |
| `compiler/src/preprocessor/preprocessor.{hpp,cpp}` | Session and form processing                                      |
| `compiler/src/preprocessor/directives.{hpp,cpp}`   | Directive grammar and parsed values                              |
| `compiler/src/preprocessor/macros.{hpp,cpp}`       | Definition table, argument collection, expansion/stringification |
| `compiler/src/preprocessor/includes.{hpp,cpp}`     | Resolution policy and inclusion context                          |
| `compiler/src/preprocessor/conditions.{hpp,cpp}`   | Branch state and restricted expression evaluation                |
| `compiler/src/preprocessor/builtins.{hpp,cpp}`     | Context macros and function-header recognition                   |
| `compiler/src/preprocessor/features.{hpp,cpp}`     | Baseline catalog, configuration, keyword changes                 |
| `compiler/src/driver/`                             | CLI integration when extracted from `main.cpp`                   |
| `tests/compiler/preprocessor/`                     | Component tests and optional OTP oracle harness                  |
| `tests/fixtures/preprocessor/`                     | Versioned positive/negative/interaction fixtures                 |
| `compiler/src/stage_readers/preprocessed/`         | Reserved directory only                                          |

Move headers needed across components under
`compiler/include/erlang_aot/compiler/` when actual consumers justify it. The
source locations above do not require a new public library or ABI contract.

## Milestones

- Steps 1–3: buildable parsing foundation, reliable locations, and oracle harness.
- Steps 4–7: macro expansion and definedness-based conditional compilation.
- Steps 8–9: headers and contextual compatibility macros.
- Steps 10–12: expression conditions, feature controls, and user diagnostics.
- Step 13: usable preprocessing check and evidence of complete chapter coverage.

Resolve ambiguous behavior through small fixtures before encoding it into APIs.
Use the pinned [epp source](../references/otp/lib/stdlib/src/epp.erl) and
[test inventory](01-pp-otp-tests.md) when resolving an algorithm or edge case.
